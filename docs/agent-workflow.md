# Agent 工具、研究流程与代码职责

本文件是当前项目的研究接入合同。默认诊断 CLI 注册 6 个只读证据工具。框架已支持 ReAct、计划执行和 Reflection 等策略，可选 `OptimizationToolbox` 将已有工作区、计划审阅和实验回调接入这些策略；Docker 训练、预测、独立评分与实际费用控制由宿主配置的可信 runner 负责。业务执行由四阶段协调器组织，状态、预算与项目账本已接入。实现入口与边界见[Agent 框架与扩展](agent-framework.md)。

## 一、基本流程

目标是围绕推荐模型提出可检验方案，在明确条件下验证，交付有证据的结论及可复现代码。有效负结果和“不足以下结论”都可以正常完成研究任务。

| 阶段 | 输入与动作 | 必须保存的结果 |
|---|---|---|
| 理解背景 | 读取任务、源码、历史证据；复用历史基线或调用实验工具建立基线 | 背景、基线与缺口 |
| 提出假设 | 登记修改、收益链路、预期过程观察和风险 | 结构化假设 |
| 模型实验 | 补丁、检查、训练、预测与验证集评分 | 源码快照、日志、checkpoint 与独立评分 |
| 结果分析和得出结论 | 比较指标、保留或否定、恢复最佳源码和生成报告 | 决策、证据和下一步 |

诊断和优化设想没有固定先后顺序。可以从异常观察提出假设，也可以从用户方案或理论先验出发，再寻找验证依据。提交实验计划前只要求方案可检验、对照清楚、判断规则明确，不要求提前证明优化一定有效。

程序运行失败进入调试与修复分支；有效实验未提升进入结果分析分支。两者分别保存。`completed` 表示执行完成，不表示推荐效果提高。

## 二、什么是足够的证据

每项实测结论应指向可核验的产物版本或哈希、JSON Pointer 或代码位置，并记录数据、协议、源码、配置、种子等适用条件。报告同时保留矛盾证据和未完成验证。

| 结论种类 | 可以声称什么 | 还不能据此声称什么 |
|---|---|---|
| 可定位的观察 | 固定验证集及协议下，某分桶指标或代码行为具有某种表现 | 已发现唯一原因，或历史结果适用于当前候选 |
| 待检验的推断 | 某种采样、损失或结构调整有理由值得实验 | 该机制已经被证明，或方案必然有收益 |
| 有效对照实验 | 在记录的条件下，候选与基线的指标、成本存在给定差异 | 单次结果等于稳定收益，或离线差异等于线上收益 |
| 机制验证 | 按需进行的消融支持特定解释；默认不重复训练种子 | 超出这些数据、配置与验证范围的普遍结论 |

程序验证回答“是否按协议正确运行”；效果验证回答“在当前条件下是否优于基线”；机制验证回答“为什么产生差异”。需要解释机制时才增加对应验证，不把因果证明作为首次实验门槛。

现有 `compare_reports` 的配对用户 bootstrap 反映用户抽样不确定性，不反映训练随机性；默认单个种子不提供跨种子稳定性结论；不同 Profile、用户、目标、过滤规则或评分协议不能直接比较。具体口径见[独立评分协议](grading-protocol.md)。

## 三、工具目录

能力目录由 `reclab_agent.tools.tool_catalog()` 提供，条目包含 `name`、`group`、`availability` 和 `responsibility`。`available` 表示当前已注册，`planned` 表示待接入。目录不是执行注册表，只有 `RecLabToolbox.specs` 中的工具会被转换成模型函数定义。

| 分组 | 工具 | 状态与职责 |
|---|---|---|
| 证据 | `list_evidence`、`inspect_artifact` | 已注册：发现证据并检查身份、文件大小及 JSON 元信息 |
| 证据 | `read_json_values`、`compare_numeric_values` | 已注册：按 Pointer 读取实测数值并做确定性比较 |
| 专项诊断 | `diagnose_beam_gap`、`diagnose_frequency_gap` | 已注册：分析项目内固定 G2/B1 报告，不是通用研究的必经阶段 |
| 知识 | `search_knowledge` | 待接入：检索登记资料，返回来源、位置和版本 |
| 工作区 | `search_source`、`read_source` | 待接入：定位并读取登记的候选源码和配置，返回内容身份 |
| 工作区 | `apply_patch`、`validate_candidate` | 待接入：在批准范围内应用哈希校验补丁，返回真实 Diff，并检查语法与入口协议 |
| 实验 | `submit_experiment`、`get_experiment`、`cancel_experiment` | 待接入：提交已批准实验，查询状态、有限日志和产物，取消并报告实际停止确认状态 |
| 评测 | `compare_experiments` | 待接入：读取独立评分报告，核验比较条件，返回整体、分桶及适用的不确定性分析 |

“诊断”“思考”“提出假设”“解释结果”是 Agent 的推理职责，不另建空泛工具。研究计划和研究结论采用结构化输出，由协调器保存，也不需要模型逐步调用“算哈希”“记预算”“冻结源码”等内部操作。

上述目录描述默认证据工具箱。可选 `OptimizationToolbox` 额外提供 `read_source`、`apply_patch`、`validate_candidate`，配置可信 runner 后再提供同步 `run_experiment` 与 `get_experiment`。它不将目录中的异步 `submit_experiment` 自动接上线；未实际注册的名称仍返回 `UNKNOWN_TOOL`。

## 四、按研究计划审阅

用户先审阅一份研究计划，计划至少包含：问题及假设、证据与缺口、基线/数据/协议引用、候选上限、允许修改的文件、对照与判定规则、资源预算及停止条件。

批准的是这份计划及其版本所界定的范围，不是每一条训练命令。范围内允许自动修复程序问题、执行批准的候选及重复实验。更换研究假设、增加候选、超出文件或实验配置范围、增加预算时，应形成新版本并重新审阅。确认实验若不在原计划和预算内，也需另行审阅。

在审阅前可读取上下文和搜集依据；修改候选和启动实验属于审阅后的动作。缺少匹配基线时，复现基线本身应进入计划并计入预算。已有、身份匹配的基线可以复用，不能只因为名称相同就复用。

上述审阅、动作校验与预算扣账是研究协调器的接入要求。可选优化工具会在写入和运行前校验匹配的 `PlanReview`，计数单实例中的补丁、实验尝试和预留训练秒数。审阅记录由可信宿主传入，模型生成的计划或反思不能自行批准执行；跨进程预算和实际费用执行仍需协调器与 runner。

## 五、Agent 与系统的责任

Agent 负责提出假设、选择证据、设计修改、解释有效实验和建议下一步。协调器负责阶段依赖、计划审阅状态、权限和预算等可计算约束，不能仅依赖 Prompt 提醒。

当前 `OptimizationAgent` 会在运行前注入任务、研究计划及目标模型上下文：可编辑文件、允许候选与种子、基线、数据 Profile、评价协议、指标和预算由可信宿主提供，模型无需猜测工具参数。四阶段共享任务范围与预算；模型不能扩大启动时授权的范围。

当前协调器和执行层承担以下职责：

- 注入任务上下文、登记资源、历史状态和剩余预算；只向模型提供当前阶段允许且实际已注册的工具。
- 校验可修改范围和计划版本，冻结源码并绑定数据、配置、镜像、种子与实验身份。
- 幂等提交，断线后先查已有作业；启动预测和外部评分，保存完整产物引用。
- 为模型调用、补丁、失败训练、修复重跑和确认实验分别按其资源消耗记账；不自动扩大预算。
- 监督超时与取消；停止未确认时保留真实状态，不把断线等同于训练退出。
- 冻结交付方案的源码、配置、权重及验证集评分证据；默认不要求测试集评估，不向模型开放测试标签读取或调参接口。

当前 `Budget` 默认限制 3 次训练、单次 600 秒、总训练 1800 秒、6 次补丁和 20 元成本，但声明这些字段不等于执行层已经统一扣账。上述 3 次训练是基线与候选的总作业次数，不是同一方案重复 3 个种子；默认每个方案使用同一个固定随机种子训练和验证集评估一次。实际以任务配置为准，不能悄悄追加实验。

达到目标、预算耗尽、重复相同失败且没有新证据、无法取得必要依据或执行环境不可用时停止，报告已有事实和未完成项。停止原因不改变有效负结果的价值。

## 六、代码职责与实施边界

| 位置 | 职责 |
|---|---|
| `core/`、`agents/` | 通用运行时、策略与优化 Agent 组合 |
| `tools/` | 工具 schema、处理函数、能力组、共享上下文与工具箱 |
| `workflow/` | 四阶段协调器、阶段规范与共享预算 |
| `application/`、`cli/` | 应用装配、启动检查、归档与命令入口 |
| `domain/` | 任务、计划、实验、结论和配置契约 |
| `experiments/`、`execution/` | 实验流水线与 Worker/SSH/Docker 执行 |
| `memory/` | 项目账本、Git、Wiki、检索与运行状态 |
| `data/`、`evaluation/`、`reporting/` | 数据适配、独立评分与报告 |
| `integrations/`、`infrastructure/` | 外部服务客户端与共享文件能力 |

逐文件导航与新增代码的放置规则见[项目架构与代码导航](architecture.md)。

旧阶段及其权限表已删除；`StudyStage` 描述当前四阶段业务流程。研究计划、实验记录和研究结论与既有 `TaskSpec` / `JobSpec` 分开，避免改变历史作业身份和存储格式。

Python 使用方按上述子包职责导入，原 `research/`、`_execution/` 与平铺业务模块已迁移；根目录命令入口保留。

这些契约已提供可独立使用的检查：`ResearchPlan.validate_for_task(task)` 核对任务身份和预算上限；`plan_hash` 绑定整份计划，包括候选、文件、种子、判断规则和预算。可信入口记录用户审阅后，`require_plan_approval(plan, review)` 拒绝缺失、否定或内容已经变化的审阅记录，`plan.check_scope(...)` 核对候选、文件及种子范围。它们不认证审阅者，也不代替协调器的权限、实时预算与状态管理，不能由模型自行生成一个 `PlanReview` 就获得执行权限。

三类主要契约均可通过 `to_dict()`、JSON 和 `from_dict()` 往返，并复用 `ArtifactStore.put_json()` 保存，无需迁移现有数据库。`ExperimentRecord` 只有在程序验证通过、训练与预测作业引用完整且存在独立评分产物时才接受 `completed`；执行失败不能携带有效评分。`ResearchConclusion` 将观察、推断和假设分别标记，观察必须带证据引用，负结果和不确定结果均可正常记录。

项目已接入可持久恢复的协调器、账本与检索；真实 GPU 与 Tavily 验收状态见[优化记录](optimization-log.md)。合成 Demo 明确 `llm_connected=false`，不能作为真实模型优化完成证据。

本次结构回归重点是规范模块导入、既有 6 工具行为、实验持久化兼容及打包完整。Agent 旧入口的迁移应与实验协议兼容分别检查。后续完整闭环还需覆盖：两种研究起点、未审阅拒绝执行、范围内修复、有效正/负/不确定结果、协议不匹配拒绝比较、恢复不重复训练、预算耗尽及证据可追溯。真实容器、GPU 和推荐质量验收应分别报告，不能由 FakeDocker 测试推出。
