### 一、问题：装好依赖，为什么还不能直接运行 Agent 写的代码？

你熟悉 PyTorch 环境：两个项目可能依赖不同版本的库。venv 为每个项目提供独立的 Python 包目录，解决“用哪套解释器和依赖”。但它没有撤销当前用户读写文件、联网或启动进程的权限。候选代码即使在 venv 中，也可能覆盖数据或者占满机器。

容器增加文件系统、进程和网络等执行边界；镜像是环境模板，容器是其运行实例。容器仍使用宿主内核，因此还要限制用户、挂载、网络和资源。将 venv 理解为“依赖管理”，将容器理解为“受配置约束的执行环境”，两者解决不同层面的问题。[Python venv 官方说明](https://docs.python.org/3/library/venv.html)

**小例子。** 两个候选都把文件写到 `/output/predictions.json`。只要各自挂载不同输出目录，它们可以使用相同容器路径，却不互相覆盖。数据目录挂为只读，表示候选可读取输入而不能修改；输出目录可写，用来保存权重和预测。容器根目录只读也不能自动使所有挂载只读，挂载权限仍要单独配置。[Docker 运行与资源约束](https://docs.docker.com/engine/containers/run/)

**对应 RecLab。** 编辑发生在控制平面的候选工作区，提交时生成源码快照；Linux Docker Worker 仅执行登记快照。本次在 WSL2 CPU 主机实测，云端/GPU 为后续验收。测试标签、宿主凭据和 Docker Socket 不挂进去。镜像提前准备依赖，运行阶段禁网，避免候选临时改变依赖环境。

**练习。** 把整个项目目录读写挂载给容器，再设“根目录只读”，评分器和测试标签就受保护了吗？

**参考答案。** 没有。读写挂载可能仍允许修改其中的评分器；可读测试标签也会破坏评测。应只挂载必要子目录，输入与源码只读，独立输出可写，评分器和测试标签留在候选环境之外。

### 二、问题：实验超时，为什么不能只让网页停止等待？

提交请求、训练进程和页面连接有不同生命周期。页面断开只说明观察通道中断，不能推出训练停止。CPU、内存、进程数和运行时长也属于不同约束：限制 CPU 不能防止内存耗尽；内存上限不能防止无限循环。GPU 配额另需按实际运行环境配置。

异步任务先返回作业身份，再独立查询状态。Worker 的作业状态包含 `queued → launching → running → completed/failed/timed_out/cancelled`，还保留 `reconciling/stopping/lost` 表达不确定结果；它与 `RunStore` 的研究任务状态分别管理。取消操作应先发出停止请求，再确认容器已退出；发出请求后不能立刻宣布取消完成。

**流程示意，不是可直接运行的 API 代码：**

```text
提交源码与资源限制 → 得到 job_id
页面断线 → 重新连接 → 查询同一个 job_id
超时 → Worker 停止容器 → 确认退出 → 保存终态和日志
```

**对应 RecLab。** `RunStore` 保存研究任务和事件；Worker 的独立 SQLite 保存 Job ID、容器身份、deadline、退出原因和产物回执。`demo status` 明确返回缓存状态与 `live_verified: false`，实时停止仍需 fresh inspect。研究任务完成，不等于所有训练作业天然都有正确终态。

**练习。** 训练已开始，SSH 返回前断线。你应该重新提交，还是先查询？

**参考答案。** 先按稳定作业身份查询。不能把网络错误当成“没有执行”；无法确认时保留待核验状态，避免重复占用 GPU。

### 三、问题：相同实验点两次，如何避免训练两遍？

幂等表示重复请求得到同一逻辑效果。它不是“参数看起来一样”，而是使用稳定身份，例如源码哈希、数据版本、镜像摘要、配置和随机种子共同确定实验键。不同种子的重复试验是不同实验；同一实验键的通信重试不应重复启动。

关键难点是“检查不存在”和“创建”之间可能并发。仅写 `if not exists: start()` 仍会启动两次。当前实现以唯一键、事务和 OS 作业锁保护记录与 Docker 副作用，并用确定容器身份恢复；本地数据库与 Docker daemon 之间不存在天然的跨系统原子事务。

**对应 RecLab。** 源码哈希、不可变快照和 SQLite 已连接真实 Worker。模拟测试注入“daemon 接受操作但响应丢失”，真实 CPU 测试核对重复提交和 Worker 重建前后的 Job ID、容器 ID、StartedAt 相同。两类证据互补，不能把模拟响应丢失说成所有网络故障均已实测。

**练习与参考答案。** 只修改学习率，实验键应不应该变化？应该，因为配置不同。容器崩溃后，能不能把同一键直接改成“成功”？不能；保留失败证据，重试需有明确尝试记录，成功仍需实际产物与评分。

完成本节后，请用自己的话画出“浏览器—控制平面—Worker—容器”四者关系，并分别标出：依赖由谁固定、预算由谁计数、进程由谁停止、指标由谁计算。

### 四、实战课：互斥做对了，为什么还要独立 Watchdog？

假设 A 持有作业锁后暂停。OS 锁可以阻止 B 重复启动同一实验，但如果取消也必须等 A 释放锁，已经运行的容器便无法及时停止。当前独立 Watchdog 只拥有停止权，不会提交、创建或启动候选：先持久化停止意图，核对 Worker/Job/规格标签，再按不可变容器 ID 发 KILL 并重新 inspect。KILL 不等待 launcher 作业锁；终态记账暂时被锁住时，可以同时出现“容器已退出”“数据库仍 stopping”。应保留这两个事实，不能为界面整齐而提前改写状态。

SQLite 写事务也可能被暂停，因此停止意图另写入私有、fsync 的 `stop-journal`，恢复的 launcher 启动前后都检查它。停止确认只绑定本次观察时点；一次 tick 并不能阻止未来迟到的 create/start，所以独立监督和持久意图需保留。即使数据库已 completed/failed，取消仍重新检查容器，不能把历史终态当作当前退出证明。

本轮真实 CPU 验收还发现日志配置缺陷：`local` 驱动默认压缩，而 `max-file=1` 与该配置不兼容，容器未正常运行、日志收集也失败。修复是每容器显式 `compress=false`。FakeDocker 没实现驱动参数校验，所以模拟全绿仍可能漏掉真实环境问题。排查训练无输出时先核对容器 create/start、inspect 与日志，不应先改模型。

**推演题一。** start 发出后连接断开，能否直接重跑？**答案：**不能；按原 Job/容器身份核验，响应丢失不等于没有启动。

**推演题二。** A 持锁暂停且 deadline 已过，应先等锁释放才停止吗？**答案：**不新增训练；独立监督先写停止意图，再核对不可变容器 ID 并停止，退出确认与终态记账分别报告。

**推演题三。** Mock 通过、真实容器无训练输出，历史 completed 又遇到容器重启，应信哪个？**答案：**首次先查 daemon/日志配置；当前停止看 fresh ownership/ID/退出检查，不能信历史终态。结果注明观察时点并保持独立监督。

### 第2周实战课：租约过期后，为什么同一任务又跑了一遍？

这次审查实际复现了一个错误：数据库已经记录 `completed`，容器却再次变为 `running`。问题发生在控制程序，不需要候选代码主动攻击。

#### 先沿时间线推演

时刻1000，Worker A领取作业，数据库lease到1060，并创建容器。A读到容器状态为 `created`，随后暂停。时刻1061，Worker B发现lease过期，接管同一作业，启动容器并等到退出，收集产物后记为 `completed`。A恢复，却仍拿着暂停前的 `created` 快照，于是再次执行 `docker start`。模拟中启动次数变为2，数据库仍是完成，容器已重新运行。

lease表示“在一段时间内由谁负责”，过期便允许接管；它不能证明旧进程已经死亡。暂停、慢磁盘或长调用都可能让活进程超过租约。数据库唯一键防重复建账，终态不可改写防状态倒退，两者都不能撤销已经发给Docker的命令。

确定容器名也不够。它能让第二次 `create` 发生名称冲突，但Docker允许 `start` 一个已经退出的同名容器。这会重新执行入口，不会创建第二个名字。

#### 为什么再查一次状态还不够

在 `start` 前重查数据库，能缩小窗口，却仍可能出现“查到未完成→暂停→别人完成→恢复后启动”。检查与动作之间存在时间差，称为TOCTOU。要解决问题，需要让竞争者无法插入这整段操作，不能只增加检查次数。

当前实现为同一主机、同一作业的锁文件加OS独占锁，覆盖检查、create/start/kill和收集。活进程暂停时仍持锁，另一Worker即使看到lease过期也不执行Docker副作用；进程崩溃后，OS释放锁，恢复者再按数据库和真实容器状态接管。锁文件保留，避免删除后产生两个不同文件各自“成功加锁”。

取消仍先持久化停止意图。若launcher正持锁，取消方返回 `stopping`，不会把“请求已提交”说成“进程已退出”；launcher在启动前后检查意图，并在锁内确认停止。lease负责恢复线索，OS锁负责本机互斥，二者职责不同。

#### 另一个真实缺陷：看见seccomp就算通过？

旧检查只搜索字符串 `seccomp`，因此 `name=seccomp,profile=unconfined` 也被接受。unconfined明确表示没有施加该过滤策略。现在解析选项并拒绝此配置。能力报告通过后，仍需在真实容器内核验过滤状态；字符串检查不是运行证据。

#### 练习与答案

练习：A读到 `created` 后暂停65秒。B发现lease过期，但抢不到OS锁，应启动、取消，还是返回当前状态？

答案：返回当前状态，不执行Docker动作。不能把A暂停当成A死亡。若用户此时取消，先记录停止意图；A恢复后处理该意图。只有确认停止，才进入取消终态。

本次本地模拟回归验证了时间线和拒绝条件，独立进程测试验证了本机锁互斥；它们没有运行候选容器。Linux锁分支随后已在云端用FakeDocker通过实机测试；真实Docker启动/退出、断线恢复与取消故障仍待验收，不能用模拟通过替代。

### 2026-10-20：从真实云环境理解依赖、配额与隔离

环境预检已完成，Worker开发与隔离验收尚未完成。SSH和PyTorch/CUDA微型计算通过，但当前AutoDL实例本身是容器，未发现Docker CLI或Docker Socket。外层容器不等于RecLab已经能为每个候选创建独立沙箱；给实例装一个Docker命令，也不代表有可工作的daemon和GPU容器权限。现阶段仅做可信环境检查，不把Agent生成的训练代码、候选推理或权重加载直接放进这个实例执行。

这次有两个实际学习点。第一，非交互SSH不一定加载交互式Conda初始化，因此固定解释器绝对路径比依赖`python3`或`conda activate`更可靠。第二，`nproc`显示256、`free`显示755 GiB属于更大的宿主视图；cgroup的`cpu.max=1500000 100000`表示每100000微秒周期最多使用1500000微秒CPU时间，即15个CPU时间配额，`memory.max=85899345920`是80 GiB内存上限。不能按宿主数字配置作业并发；这些配额也还不是每个RecLab作业的独立限制。

练习：GPU张量计算成功，能否勾选“真实云端容器运行与标签隔离通过”？不能；它仅证明当前解释器可以使用GPU。还需实际验证候选的输入只读、测试标签与凭据不可见、禁网、作业资源限制、超时/取消和独立评分。证据：`reports/cloud-environment-2026-10-20.json`。下一步继续实现Worker，并核验可用的Docker隔离执行环境，不静默回退到直接运行候选。
