# 第6周学习正文：把长实验变成可靠的服务

适合已有推荐算法基础、正在系统学习 Agent 的读者。下面的接口与代码都是**设计示例**，不是当前仓库已经验收的 API。学习完成与功能完成分别记录。

## 先思考一个问题

你点击“优化低频商品推荐”，训练需要20分钟。第3分钟关闭网页，第5分钟网络恢复并再次点击。系统应继续原实验、重新训练，还是取消？这个问题涉及三个寿命：HTTP请求通常很短，Agent任务包含多步决策，训练作业可能持续很久。把它们绑在一个请求里，页面断线就难以判断实验究竟有没有启动。

## 原理：请求、任务和作业分开管理

HTTP层负责校验、登记和返回任务标识；控制器负责推进任务；Worker负责运行训练。数据库中的状态是事实来源，网页是状态的一个视图。因此关闭页面不等于取消实验，浏览器也不负责保管唯一的实验状态。

提交后返回HTTP 202，表示已接受处理，不表示任务已经完成，更不保证最终成功。响应应给出当前状态及查询入口；这个语义来自[HTTP规范](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。

设计示例：

```text
POST /tasks  →  202 {task_id: "t17", status: "queued"}
GET /tasks/t17  →  {status: "running", job_id: "j09"}
GET /tasks/t17/events  →  持续推送持久化事件
```

`queued → running → completed/failed/cancelled`必须与实际执行一致。收到取消请求时先记录取消意图，Worker确认停止后才能标记cancelled；停止失败要如实呈现。

## 原理：SSE负责通知，持久化事件负责恢复

SSE是服务端向浏览器单向发送事件的HTTP流，适合展示计划、日志和实验状态。每条事件在本任务内分配递增ID，先落库再推送，格式以空行结束：

```text
id: 18
event: job_status
data: {"job_id":"j09","status":"running"}

```

同一个EventSource断线重连时，可通过`Last-Event-ID`报告最后接收的ID；服务端据此补发之后的事件。协议本身不替你保存历史，也不保证业务处理恰好一次。[SSE标准](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)

例如界面处理到18，重连补发19、20，同时收到重复18：客户端按ID去重，仍以查询到的任务快照校准。整页刷新会创建新的EventSource，应由应用保存游标或重新获取快照，不能依赖旧对象的记忆。游标过旧、历史已清理时，也应返回快照让界面重建。

## 原理：幂等解决“回复丢了，再提交一次”

幂等指重复同一操作不产生额外业务效果。POST本身不天然幂等，RecLab需要应用协议：同一幂等键和同一任务内容返回已有task_id；同一键对应不同内容则拒绝。数据库唯一约束处理两个请求同时到达的竞争。Worker还需根据作业身份查询已有容器，不能只在浏览器禁用按钮。用户明确要求独立复跑时，才创建新的试验身份。

模型回答、日志和Diff也属于不可信文本。把`<img src=x onerror=...>`直接交给`innerHTML`会让浏览器解析HTML。普通`pre`元素应使用`textContent`；需要Markdown排版时另做可靠净化，链接仍需校验。[OWASP说明](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html#safe-sinks)

## 在RecLab里边学边做

先画清“提交任务—控制器—Worker—事件库—网页/CLI”的边界，再用假Worker观察断线。练习成功后才能接真实训练；一次页面演示不能代替恢复和取消验证。

1. 服务已创建t17，但202响应丢失，客户端带原键重试，应发生什么？
2. 界面最后处理ID=18，收到18、19、20，应展示几条新事件？
3. Worker失联后，网页能直接显示failed吗？

## 参考答案

1. 返回同一个t17；唯一键约束和作业查询共同避免重复训练。
2. 两条。处理19、20；重复18不再次追加。随后核对状态快照。
3. 不能仅凭页面超时判断实验失败。先呈现未知或失联状态，查询执行端；确认终态后更新，避免留下仍在收费的孤立实验。
