# 第2周实战课：租约过期后，为什么同一任务又跑了一遍？

这次审查实际复现了一个错误：数据库已经记录 `completed`，容器却再次变为 `running`。问题发生在控制程序，不需要候选代码主动攻击。

## 先沿时间线推演

时刻1000，Worker A领取作业，数据库lease到1060，并创建容器。A读到容器状态为 `created`，随后暂停。时刻1061，Worker B发现lease过期，接管同一作业，启动容器并等到退出，收集产物后记为 `completed`。A恢复，却仍拿着暂停前的 `created` 快照，于是再次执行 `docker start`。模拟中启动次数变为2，数据库仍是完成，容器已重新运行。

lease表示“在一段时间内由谁负责”，过期便允许接管；它不能证明旧进程已经死亡。暂停、慢磁盘或长调用都可能让活进程超过租约。数据库唯一键防重复建账，终态不可改写防状态倒退，两者都不能撤销已经发给Docker的命令。

确定容器名也不够。它能让第二次 `create` 发生名称冲突，但Docker允许 `start` 一个已经退出的同名容器。这会重新执行入口，不会创建第二个名字。

## 为什么再查一次状态还不够

在 `start` 前重查数据库，能缩小窗口，却仍可能出现“查到未完成→暂停→别人完成→恢复后启动”。检查与动作之间存在时间差，称为TOCTOU。要解决问题，需要让竞争者无法插入这整段操作，不能只增加检查次数。

当前实现为同一主机、同一作业的锁文件加OS独占锁，覆盖检查、create/start/kill和收集。活进程暂停时仍持锁，另一Worker即使看到lease过期也不执行Docker副作用；进程崩溃后，OS释放锁，恢复者再按数据库和真实容器状态接管。锁文件保留，避免删除后产生两个不同文件各自“成功加锁”。

取消仍先持久化停止意图。若launcher正持锁，取消方返回 `stopping`，不会把“请求已提交”说成“进程已退出”；launcher在启动前后检查意图，并在锁内确认停止。lease负责恢复线索，OS锁负责本机互斥，二者职责不同。

## 另一个真实缺陷：看见seccomp就算通过？

旧检查只搜索字符串 `seccomp`，因此 `name=seccomp,profile=unconfined` 也被接受。unconfined明确表示没有施加该过滤策略。现在解析选项并拒绝此配置。能力报告通过后，仍需在真实容器内核验过滤状态；字符串检查不是运行证据。

## 练习与答案

练习：A读到 `created` 后暂停65秒。B发现lease过期，但抢不到OS锁，应启动、取消，还是返回当前状态？

答案：返回当前状态，不执行Docker动作。不能把A暂停当成A死亡。若用户此时取消，先记录停止意图；A恢复后处理该意图。只有确认停止，才进入取消终态。

本次本地模拟回归验证了时间线和拒绝条件，独立进程测试验证了本机锁互斥；它们没有运行候选容器。Linux锁分支随后已在云端用FakeDocker通过实机测试；真实Docker启动/退出、断线恢复与取消故障仍待验收，不能用模拟通过替代。
