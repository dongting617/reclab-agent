# RecLab Agent 重构与功能完善实施方案

代码已按职责重组，当前目录与导入路径以[项目架构与代码导航](architecture.md)为准。

需求依据：[功能需求](plan.md)。更新日期：2026-11-23。

状态：主要代码实现和离线验收已完成；真实模型工具接口已验证。真实 GPU 验收被当前 SSH 连接拒绝阻断，Tavily 缺少本地 Key，尚未联网实测。需求细节保留如下，实际使用见[研究使用说明](research-usage.md)，证据见[验收记录](../reports/implementation-20261123.json)。

## 1. 目标与实施顺序

将 RecLab 完善为受预算约束的推荐模型优化 Agent，严格遵循四阶段业务流程：

**理解背景 → 提出假设 → 模型实验 → 结果分析和得出结论。**

先完成现有代码重构及验收，再实施实验账本、记忆、文献调研和过程指标，不将两部分混在同一次改造中。

固定约定：

- 推荐任务优先，CLI 为主要验收入口。
- 用户启动时授权目标、数据、可修改范围和总预算，范围内自主研究。
- 基线与候选使用同一个固定随机种子，默认 2026。
- 默认每个方案训练一次，统一使用验证集评估。
- 历史基线满足条件时复用，不强制重新训练。
- 时间、作业次数、模型请求次数和联网请求次数实行硬限制；人民币费用不承诺硬封顶。
- 首版支持研究任务与远程作业恢复，不支持训练中间 epoch 续训。

## 2. 基线确定与四阶段流程

### 2.1 理解背景

读取建模目标、训练和验证数据、指标、源码、历史实验及相关经验，形成 `BackgroundContext`。

**基线确定属于本阶段，不要求先提出优化假设。**

按以下顺序确定基线：

1. 用户显式指定历史实验时，校验并使用该实验；不符合条件则明确报错。
2. 未显式指定时，检查项目登记的当前已接受方案，满足当前比较条件则作为基线。
3. 否则查找与配置中的初始模型、配置和比较条件匹配的历史基线。
4. 没有可复用记录时，调用实验工具训练并评估初始模型，建立基线。
5. 基线无法获得有效评分时停止研究，保存失败或证据不足报告，不继续声称候选有收益。

历史复用至少核对：

- 模型任务及接口、数据内容和划分、评分协议。
- 随机种子及训练配方；执行环境和资源限制是否满足当前比较要求。
- 实验状态、评分文件及证据哈希。
- 对应源码、配置和 checkpoint 是否可定位且完整。

自动选择使用明确登记的“当前已接受方案”，不通过未经核验的报告文字或单纯最高分选择基线。复用来源和适用条件必须写入当前报告。

复用历史实验不扣新的训练次数，但本轮查询、核验和模型调用照常计入预算。新跑基线计入当前任务总预算。

### 2.2 提出假设

基于背景、基线、历史实验和文献生成 `HypothesisSpec`，包括：

- 优化假设及支持、反对证据。
- 拟修改的模型或训练部分。
- 可验证的收益链路。
- 过程指标及预期观察。
- 潜在风险、验收条件和停止条件。

没有文献来源或过程证据时明确标记缺口，不用模型推测补造事实。

### 2.3 模型实验

按假设执行：

**读取源码 → 修改模型及诊断代码 → 静态检查 → 受控 Smoke Test → 训练 → 预测 → 验证集独立评分 → 保存实验记录。**

程序错误允许在预算内修复。每次实际训练、失败尝试及源码变化均留记录。

基线建立与候选实验使用同一套实验工具和 Runner，但调用条件不同：

- 背景阶段只允许运行登记的基线源码，不允许修改模型。
- 候选实验必须绑定已校验的假设，并处于模型实验阶段。
- 训练、预测和正式评分继续采用固定复合流程，不能由模型选择跳过评分。

### 2.4 结果分析和得出结论

输出 `ResearchDecision`：

- 对比基线与候选的最终指标、过程指标和资源使用。
- 区分实测观察、机制推断和信息缺口。
- 决定保留、否定或证据不足。
- 保存报告、最佳源码引用及下一步建议。

需要继续优化时返回“提出假设”；缺少背景证据时返回“理解背景”。预算不足或没有可检验的新方案时停止。

## 3. 第一部分：现有代码重构

### 3.1 删除旧八阶段

删除旧八阶段枚举、阶段权限表、`stage_tool_names`、对应公开导出、测试及文档说明，不保留别名或八阶段兼容映射。

移除当前流程中的独立“确认训练”分支和相关活动配置。历史报告中的原始字段保留为历史数据，不据此恢复旧流程。

旧模块中仍有价值的授权校验、范围校验和证据类型提取到对应服务；不为了兼容旧结构继续保留旧阶段体系。

### 3.2 职责分层与工具化

复用已有 `Tool`、`ToolSpec`、`ToolRegistry`，形成以下边界：

| 层次 | 职责 |
|---|---|
| Agent | 理解任务、提出假设、选择工具和解释结果 |
| 工具层 | 暴露业务能力，校验参数，返回统一结果和证据 |
| 业务服务 | 实现源码、实验、比较、报告等可复用逻辑 |
| 协调器 | 执行四阶段流程，控制范围、预算、状态和终止 |
| Runner | 运行模型代码、预测及独立评分 |

业务能力通过工具进入；底层辅助函数保持普通函数，不机械包装每个函数。Agent 不直接操作文件系统、数据库或执行器。

工具按能力组织：

- 背景：读取任务、源码、证据、历史结果、解析基线。
- 假设：登记假设、验证范围与实验条件。
- 实验：补丁、检查、运行实验、读取日志和产物。
- 分析：比较指标、登记决策、恢复最佳源码、生成报告。

工具实现不因阶段重复；阶段控制决定当前允许执行哪些操作。预算和范围检查由程序执行。

### 3.3 收敛现有模块

- 启动器只负责配置、依赖装配和启动协调器，删除无条件重跑基线及“至少两次训练”的前置假设。
- `OptimizationAgent` 负责阶段内模型交互，不再承担整体业务编排。
- `OptimizationToolbox` 组合 `tools/` 下的能力组；`StudyContext` 单独保存共享状态、授权和恢复信息。
- 从策略对比脚本提取最佳源码恢复、重复实验检查和指标比较；脚本复用公共工具。
- 报告整理与 Markdown/HTML 渲染分开，统一消费结构化结果。
- 保留 ReAct、PlanExecute、Reflection 等策略，不将它们解释为业务阶段。
- 工具目录的可用状态与实际注册结果保持一致。

### 3.4 重构验收

完成以下检查后才进入第二部分：

- 四阶段可由脚本后端完整执行，顺序和阶段输出可检查。
- 支持通过显式历史报告复用基线，无需先实现长期记忆。
- 无历史基线时，可在背景阶段运行基线实验。
- 有历史基线且只剩一次训练额度时，仍能运行一个候选。
- 阶段切换不重置预算，背景阶段不能修改模型或运行候选。
- 旧八阶段代码、导出和活动文档均已删除。
- 旧配置、独立评分、报告、执行器及权限相关回归通过。

## 4. 第二部分：账本、记忆与自主研究能力

### 4.1 项目资源与实验账本

每个项目建立独立本地 Git、Markdown Wiki、数据入口、产物目录及 SQLite 账本。项目包含多个研究任务，任务包含多个假设和实验。

账本保存：

- 任务、假设、文献来源、收益链路、风险和诊断定义。
- 源码哈希、Git commit、配置、数据身份、评分协议、种子和环境。
- 基线引用、作业 ID、状态、失败原因、指标、checkpoint 和日志。
- 决策、当前已接受方案、预算预留及使用事件。

正式指标由程序写入；模型解释单独保存。提交前持久化实验身份和资源预留，失败尝试同样入账。

Git 保存模型、训练和诊断代码的初始版本及各实验版本；数据和权重不进入 Git。不自动修改原源码仓库或推送远端。

### 4.2 短期记忆与恢复

保存阶段、背景、基线、假设、阶段摘要、必要消息、最佳源码、工具结果引用、预算和远程作业身份。

恢复时：

- 先核验已提交作业和已有产物，再继续执行。
- 不重复提交，不重复扣账，不重置预算。
- 单个运行只允许一个活动控制器。
- 模型重试、规划、反思和经验总结均计入请求额度。
- 已终止训练若重新运行，作为新的预算消耗，不伪装为续训。

### 4.3 可检索经验摘要

实验结束后生成经验卡片：

**条件 → 假设与修改 → 观察 → 解释与不确定性 → 决策 → 证据。**

- 正结果、负结果和程序失败分别保存。
- 使用已有 BM25；先按项目、数据和协议过滤，再检索相关摘要，默认返回 5 条。
- 新任务读取历史概览，研究过程中按需再次检索。
- 每条经验关联实验 ID、来源位置和哈希；数值结论回读原始评分。
- 摘要和索引可重建，失败不影响实验入账。
- 支持人工修订和替代标记，不覆盖原始实验事实。

基线解析工具改为查询账本，沿用第二节的选择规则。首版不引入向量数据库或知识图谱。

### 4.4 文献调研

接入 Tavily 搜索及正文提取，保存 URL、标题、获取时间、内容哈希、可读取范围和引用位置，生成 Wiki 文献笔记。

Key 通过环境变量提供；未配置或获取失败时明确提示，可继续使用本地知识。只有摘要可用时，不声称已读取全文。请求计入联网预算。

### 4.5 过程指标

增加过程指标声明与诊断工具：

- 声明定义、采集阶段、预期方向和“诊断／验收条件”用途。
- 在登记的诊断目录中允许新增代码，在 Worker 中运行。
- 基线和候选比较使用同一指标定义及版本。
- 必需指标缺失时标记证据不足；诊断指标用于分析收益链路。
- 缺少历史基线指标时，优先从已有产物重算；不能重算则明确缺失。
- 如需额外运行，必须占用剩余预算，不能因补指标重置额度。
- 正式评分器和数据协议保持只读。

## 5. 接口、文档与完整验收

### 5.1 接口与兼容

CLI 提供项目初始化、研究运行、恢复、实验查询、知识检索、历史导入和索引重建；调用公共服务，不复制实现。

配置支持项目、研究循环、诊断、知识来源及预算。旧配置通过输入适配继续使用；不保留旧八阶段 API。已有 Worker 身份哈希和历史评分不重写。

历史实验显式导入并按身份去重；证据缺失的记录标记未核验，不自动成为基线。

### 5.2 文档交付

本方案作为实施基准，在需求文档中建立引用。随后分两次更新：

1. 重构完成：更新四阶段、模块职责、工具清单、基线规则和重构验收结果。
2. 功能完成：更新账本、Wiki、恢复、诊断、Tavily 和完整 CLI 示例。

删除旧八阶段的现行设计说明；历史实验记录保持原样。本轮只修改本地文档。

### 5.3 完整验收

- 历史基线复用、新任务建立基线、证据损坏、比较条件不匹配均有明确行为。
- 正收益、保护指标下降、有效负结果、程序失败和诊断缺失均产生正确决策。
- 在提交前后、评分后和报告前中断，恢复后不重复训练或重置预算。
- 新任务能检索旧实验经验、回读证据并正确引用。
- 每个实验可定位源码、配置、checkpoint、预测和独立评分。
- 常规测试使用离线 fixture；显式验收验证 Tavily 和真实 SASRec 流程。
- 第一部分完成并验收后，才开始第二部分；最终报告明确各功能实现和实测状态。
